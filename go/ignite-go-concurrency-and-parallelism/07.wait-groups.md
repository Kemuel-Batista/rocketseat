# Go Concurrency: Sync.WaitGroup

Este documento aborda o uso de `sync.WaitGroup` em Go para orquestrar goroutines, garantindo que tarefas paralelas sejam concluídas antes que o programa prossiga ou finalize.

## O Problema da Concorrência

Em Go, quando a função `main` termina, todas as goroutines filhas são encerradas imediatamente, independentemente de terem concluído seu trabalho ou não.

Anteriormente, vimos como cancelar goroutines ou definir timeouts. Mas como garantir que uma tarefa **terminou**?

### A Abordagem "Done Channel"

Uma solução primitiva é usar canais para sinalizar o término:

1.  A goroutine envia um valor para um channel (`done <- true`) ao finalizar.
2.  A `main` bloqueia esperando a leitura desse channel (`<-done`).

Embora funcione para casos simples, essa abordagem se torna complexa ao lidar com múltiplas tarefas dinâmicas.

-----

## O Conceito de WaitGroup

O `sync.WaitGroup` funciona como um **Maestro de Orquestra**.
O dever dele é garantir que cada músico (goroutine) termine sua nota antes de seguir para a próxima parte da música. Ele age como um **contador de tarefas thread-safe**.

### Como funciona internamente

O `WaitGroup` possui um contador interno (implementado com primitivos atômicos para evitar *Race Conditions*).

1.  **`Add(int)`**: Incrementa o contador. Sinaliza quantas tarefas devem ser esperadas.
2.  **`Done()`**: Decrementa o contador em 1. Sinaliza que uma tarefa acabou.
3.  **`Wait()`**: Bloqueia a execução da goroutine atual até que o contador chegue a **zero**.

## Implementação Prática

### Exemplo Básico: Workers

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

// worker simula um trabalho.
// NOTA: O WaitGroup deve ser passado como PONTEIRO.
func worker(id int, wg *sync.WaitGroup) {
	defer wg.Done() // Decrementa o contador ao sair da função

	fmt.Printf("Worker %d starting\n", id)
	time.Sleep(500 * time.Millisecond) // Simula latência
	fmt.Printf("Worker %d finished\n", id)
}

func main() {
	var wg sync.WaitGroup // Não precisa de make()
	tasks := 5

	// Adicionamos o total de tarefas ao contador
	wg.Add(tasks)
	// Alternativa: Poderia ser wg.Add(1) dentro do loop

	for i := 0; i < tasks; i++ {
		go worker(i, &wg)
	}

	// Bloqueia até que o contador interno seja 0
	wg.Wait()
	fmt.Println("Main done")
}
```

### Regras de Ouro

1.  **Ponteiros:** Se passar o `WaitGroup` para uma função, **sempre passe o ponteiro** (`*sync.WaitGroup`). Se passar por valor, o Go cria uma cópia do contador, e o `Done()` na cópia não afetará o `Wait()` na original, causando *Deadlock*.
2.  **Defer Done:** Use `defer wg.Done()` no início da goroutine para garantir que o contador seja decrementado mesmo se a função entrar em pânico.

## Casos de Uso Reais

### 1\. Web Scraper / Batch Processing

Imagine iterar sobre uma lista de URLs para fazer *fetch* de dados (Google, Amazon, Rocketseat). O `WaitGroup` garante que todas as requisições HTTP terminem antes de consolidar os dados.

```go
for _, url := range urls {
  wg.Add(1)
  go fetchURL(url, &wg)
}
wg.Wait()
```

### 2\. Graceful Shutdown (Encerramento Gracioso)

Este é um padrão crítico em microsserviços, como um serviço de envio de e-mails.

  * **Cenário:** O serviço recebe um sinal de **SIGTERM** (pedido educado para encerrar) enquanto está processando requisições SMTP (que podem levar \>200ms).
  * **SIGKILL vs SIGTERM:** O `SIGKILL` mata o processo instantaneamente. O `SIGTERM` permite limpeza.
  * **Solução com WaitGroup:**
    1.  Ao receber o `SIGTERM`, o servidor para de aceitar novas requisições.
    2.  Ele espera (`wg.Wait()`) que as requisições de e-mail em andamento (background tasks) terminem.
    3.  Só então o processo encerra.

> **Nota:** É recomendável combinar isso com `context.WithTimeout` para evitar que uma tarefa travada ("hang") impeça o servidor de reiniciar para sempre.

## Observações sobre Pacotes Relacionados

### `sync/atomic`

Mencionado brevemente, o pacote `atomic` lida com operações de baixo nível (como o contador interno do WaitGroup).

  * **Uso:** Aplicações extremamente performáticas ou low-level.
  * **Aviso:** Requer muito cuidado. Para a maioria dos casos de sincronização, prefira **Channels** ou o pacote **Sync** (Mutex, WaitGroup).

### Resumo

Use `WaitGroups` quando você precisa esperar por um conjunto de operações concorrentes terminar e não necessariamente precisa se comunicar com elas (enviar dados de volta), apenas saber que elas acabaram.
